# 商品数据库与 SQL 查询方案

## 状态与目标

本文记录已确认的设计和采用的默认策略，是后续实施依据；不表示数据库迁移或代码改造已完成。

模型理解用户需求并抽取结构化条件。后端校验条件，按固定规则构造参数化 SQL。数据库完成匹配、筛选、排序和分页，后端只向模型返回有数量边界的商品摘要。

运行时商品查询不再依赖本地 JSON，也不把完整商品表或完整分类读入 Python 后筛选。JSON 保留为初始化数据和测试样本。

## 当前实现

- `examples/assistant/api/mock_retail.py` 从 JSON 加载商品、库存、政策和证据，在内存中搜索商品。
- `examples/demo_common/storefront_fixtures.py` 的 `rank_products()` 完成内存筛选、相关性评分、排序和结果截取。
- `shopping-agent/core/shopping_agent/backend.py` 定义 `StorefrontBackend`，作为数据库实现的替换接口。
- `shopping-agent/core/shopping_agent/executor.py` 校验工具参数并限制单次返回数量。
- `examples/assistant/api/main.py` 已接入 Supabase 会话、购物车和长期记忆持久化；实际连接和迁移状态仍需检查。
- `examples/assistant/storefront-web/lib/catalog.ts` 直接导入商品 JSON，商品浏览需要同步改为读取数据库支持的服务端接口。

## 架构与职责

```text
用户需求
  → 模型抽取查询条件
  → 工具执行器校验参数与调用预算
  → 数据库后端归一化条件并选择固定查询模板
  → PostgreSQL 执行参数化 SQL
  → 有限商品摘要与分页信息
  → 模型说明并展示商品
```

| 层 | 职责 |
| --- | --- |
| 模型 | 理解需求，提取分类、用途、预算、规格和排序意图 |
| 工具描述 | 定义参数、排序选项、分页规则和结果范围 |
| 购物 skill | 指导搜索、缩小候选、比较、补充详情和继续浏览 |
| 执行器与后端 | 强制参数白名单、数量限制、查询预算、超时和权限边界 |
| PostgreSQL | 完成条件匹配、规格关联、排序、分页及聚合统计 |

不开放模型生成或提交任意 SQL 的工具。字段、运算符和排序表达式由后端白名单决定；值通过驱动参数绑定，不拼接用户输入。数据库凭证仅保留在服务端。

## 数据库与迁移范围

沿用现有 Supabase PostgreSQL。商品查询优先由 Python 后端通过连接池直连数据库并执行 SQL；实施前验证连接方式和权限。现有身份、会话、购物车和记忆持久化接入保留。

拟议逻辑表如下，最终字段和约束由现有数据核对后确定：

| 表 | 内容 |
| --- | --- |
| `products` | 商品主体、分类、描述、上下架状态、展示顺序 |
| `product_variants` | 可购买规格、价格、重量、容量及规格值 |
| `inventory` | 各可购买规格的库存 |
| `product_evidence` | 现有价格走势和评价摘要证据，保留模拟性质说明 |
| `policies` | 配送、退换等政策 |

频繁筛选的数值使用明确的数据类型和单位；不固定的描述属性可存 JSONB。价格保留币种并使用精确数值类型。库存、价格和商品关联通过约束保证有效性。

保留原商品及规格 ID。旧商品以已下架状态保留，允许历史详情查看和购物车移除，不参与正常推荐和购买。

第一版提供可重复执行的导入脚本，不新增商品管理后台。重复导入的更新范围必须明确，不能无条件覆盖已由业务更新的库存等数据。

## 条件归一化

结构化条件是主要检索入口，关键词是补充入口。

| 用户含义 | 结构化结果 |
| --- | --- |
| 背包分类 | 映射到允许的分类标识 |
| 一公斤以内 | 重量上限 1000 克 |
| 五百元以下 | 价格严格小于 500，表达式需能保留边界语义 |
| 至少三十升 | 容量大于等于 30 升 |
| 便宜的先看 | 价格升序 |
| 轻一点 | 优先按重量升序，不擅自添加重量上限 |

后端校验分类、字段、运算符、单位、数值和排序枚举。明确条件必须进入过滤表达式，不仅放进关键词。缺失值不得冒充满足数值约束。

剩余关键词使用受控的归一化与同义词规则，在 SQL 内完成匹配和相关性排序。不得以整句标题 `LIKE` 替代分类和属性查询，也不要求原样迁移内存评分算法。通过代表性中文查询验证匹配质量。

## 查询与返回策略

| 场景 | 策略 |
| --- | --- |
| 泛分类浏览 | 默认每页 6 个，单次最多 8 个，按展示顺序和商品 ID 稳定排序 |
| 明确条件搜索 | SQL 先满足全部硬条件，再执行指定或默认排序和分页 |
| 用户指定排序 | 严格遵从价格、重量等受支持排序，以商品 ID 处理同值顺序 |
| 继续查看 | 使用绑定原查询条件和排序的游标获取下一页 |
| 数量或价格范围问题 | 数据库聚合查询，只返回统计结果 |
| 商品详情 | 按已选中的少量商品 ID 读取详情 |
| 空结果 | 明确无匹配，不自动取消预算、尺寸等硬条件 |
| 重复查询 | 同一轮相同归一化条件与游标复用结果；相关写入后使结果失效 |

“查看所有背包”表示浏览整个分类的意图，不表示一次返回全部背包。聊天展示首批并提供继续查看；完整分类通过装备页分页浏览。模型不自动循环翻页。

结果至少包含商品摘要、`has_more` 和下一页游标。可以查询页大小加一条来判断后续页面，额外一条不交给模型。不默认计算总数，不能把本页数量说成商品总数。

搜索摘要只携带推荐所需字段，不附带全部规格详情、完整评价或价格序列。前端展示和模型使用同一份服务端事实。

同一个可购买规格必须同时满足价格、颜色、尺寸、重量和库存等条件。不能使用不同规格各自满足的条件拼出不存在的可购买选项。商品族聚合与候选规格关系必须在 SQL 中保持正确。

普通分页不额外插入“多样性推荐”导致排序失真。若后续增加代表性推荐，应显式区分该模式。

## 查询预算与性能

单次数量上限之外，后端还需要可配置的单轮搜索调用次数、累计返回商品数和查询超时。成套装备规划按所需类别共享总预算，不能通过并行调用绕过限制。达到预算后返回明确的受限状态，由模型基于已有结果回答或等待用户继续。

第一版默认每轮最多 4 次搜索、累计最多 24 个候选；户外部署的首批大小默认为 6（可由 `SHOPPING_SEARCH_PAGE_SIZE` 配置），单次硬上限仍为 8。达到预算后执行器返回受限状态，模型不能通过重复或并行调用绕过它。查询超时沿用数据库客户端和部署配置，真实数据量验证后再调整。

索引按实际支持的分类筛选、价格排序、重量排序、商品规格关联和库存查询建立，避免只给每个字段单独建索引。不同范围条件和排序组合不保证共用一个索引。

`LIMIT` 只约束返回数量，不保证只扫描相同数量的记录。使用代表性数据和执行计划验证主要 SQL 的扫描、关联和排序成本。小表顺序扫描可以是合理选择；验收目标是查询成本合理，不是所有查询强制使用索引。

## Skill 与接口改动

扩充现有技能，不新增重复的数据库搜索技能：

- `shopping-agent/skills/search-discovery/SKILL.md`：补充有限候选、分页继续、结果范围和空结果处理。
- `shopping-agent/skills/outdoor-equipment/SKILL.md`：保留跨分类规划与明确约束，为每类查询分配有限候选。
- `shopping-agent/skills/purchase-research/SKILL.md`：仅对少量候选补充详情，避免为了研究读取整个分类。

简单搜索可能不加载 `search-discovery`，因此强制规则必须由工具和后端执行。每条机制只定义一处，技能描述购物行为，不重复承担代码约束。

现有搜索方法返回商品列表；分页元数据、游标和聚合能力需要同步调整类型、后端契约、工具 schema、执行器及序列化。保持商品来源记录和购物车门控有效。

新增数据库后端后，清理调用方对 `backend.products`、同步商品访问和证据读取的内存实现依赖。新增模块时更新 `AGENTS.md` 和对应 README。

## 前端与数据更新

装备列表、详情与 Agent 共用数据库支持的服务端接口。聊天每次新的查询读取数据库，本轮重复查询可复用结果。前端不能继续把导入的 JSON 当成运行时商品事实。

商品页面采用明确的缓存失效或有效期策略；具体时效在实施时确定并记录。价格和库存相关写操作重新校验数据库，不以页面缓存或模型曾经看到的结果为准。

## 实施顺序

1. 检查现有数据库连接、迁移、权限和源数据一致性。
2. 定义关系表、约束、索引和可重复执行的数据导入。
3. 实现数据库后端、固定查询模板、分页结果与查询预算。
4. 更新工具契约和现有购物技能。
5. 将装备浏览和详情切换为同一数据库数据源，配置缓存策略。
6. 验证查询语义、前后端一致性和执行计划，记录最终预算配置。

## 验收标准

- 模型仅提交结构化条件，不能控制 SQL 表名、字段表达式或任意语句。
- 商品搜索在 SQL 内完成匹配、筛选、排序和数量限制，没有全表读取后 Python 筛选路径。
- 宽泛背包查询只返回首批摘要，具有正确的分页信息，不自动遍历全部页面。
- 用户指定排序有效；相同排序值具有稳定顺序，静态数据下翻页无重复和遗漏。
- 预算、单位、边界、规格与库存组合筛选正确，零结果不放宽明确约束。
- 中文分类、同义表达和残余关键词的代表性查询返回合理候选。
- 数量和范围查询通过 SQL 聚合完成，不把所有商品交给模型计算。
- 重复调用和多分类并行调用均受本轮预算控制，预算耗尽与数据库异常能明确区分于无商品。
- 数据库商品更新后，下一次新查询读取到新事实；商品页按已记录的缓存策略更新。
- 保留历史商品 ID 和下架行为，购物车来源门控继续有效。
- 导入可重复执行且不误覆盖业务数据，主要查询在代表性数据量下具有合理执行计划。

当前第一版实现已提供 `supabase/migrations/003_catalog.sql`、`examples/assistant/api/sql_retail.py` 和 `scripts/import_catalog.py`。迁移应用、数据导入以及真实数据库上的执行计划验证仍需在目标 Supabase 项目中执行。
